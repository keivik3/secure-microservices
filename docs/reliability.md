# ДЗ 5: Надёжность системы

## 1. Параметры обслуживания

| Параметр | Определение | Целевое значение |
|---|---|---|
| **MTBF** (Mean Time Between Failures) — среднее время между отказами | Как часто сервис падает. Оценка: при корректной конфигурации отказы самих контейнеров редки, основные источники — перезапуск инфраструктуры и сетевые сбои | ≥ 720 ч (30 суток) |
| **MTTR** (Mean Time To Repair) — среднее время восстановления | Время от падения контейнера до приёма запросов. Обеспечивается `restart: unless-stopped` + healthcheck + retry-подключения | ≤ 1 мин |
| **SLO по доступности** | Доля времени, когда система принимает запросы: `uptime = MTBF / (MTBF + MTTR)` | ≥ 99,9 % (720 / 720,016) |
| **RPO** (Recovery Point Objective) — допустимая потеря данных | Частота бэкапов определяет, сколько данных мы готовы потерять | ≤ 24 ч (бэкап раз в сутки) |
| **RTO** (Recovery Time Objective) — время восстановления данных | Развернуть дамп из `backups/` скриптом `restore.sh` | ≤ 15 мин |

## 2. Отказоустойчивость — что и где настроено

| Механизм | Где реализовано | Что даёт |
|---|---|---|
| `restart: unless-stopped` | основные сервисы стандартного Compose-профиля | контейнерный движок перезапускает сервис после падения (MTTR ≤ 1 мин) |
| healthcheck + `depends_on: service_healthy` | инфраструктура → repair-service → API Gateway → frontend | сервис стартует только когда зависимость реально готова, а не просто запущена |
| Retry-подключение к БД (10 попыток × 3 сек) | `repair_service/db.py: init_db()` | не падаем, если БД ещё прогружается |
| Graceful degradation кэша | `repair_service/cache.py` | Redis недоступен → работаем напрямую через БД, запросы не падают |
| Graceful degradation брокера | `repair_service/events.py` | RabbitMQ недоступен → запрос успешен, событие теряется, ошибка в лог |
| Вечное переподключение консьюмера | `notification_service/main.py` | обрыв связи с брокером → переподключение через 5 сек |
| Ручной ack после обработки | `notification_service/main.py` | сообщение не теряется при падении консьюмера (at-least-once) |
| Durable exchange/queue + persistent сообщения | оба сервиса | сообщения переживают рестарт RabbitMQ |
| Том `pgdata` | postgres | данные БД переживают пересоздание контейнера |
| PostgreSQL streaming replication | профиль `ha-demo`, `postgres-ha-master` + `postgres-ha-standby` | physical replication slot удерживает WAL, синхронная репликация подтверждает запись только после standby; после остановки старого master standby повышается командой `pg_ctl promote` |
| RabbitMQ quorum queue | профиль `ha-demo`, кластер из трёх узлов | после потери leader оставшиеся два узла сохраняют кворум и выбирают нового leader |

Известные компромиссы (честно говорим на защите):
- при недоступном брокере событие теряется — в продакшене нужен outbox-паттерн (событие сначала пишется в БД транзакционно, затем вычитывается ретраером);
- переключение PostgreSQL в учебном стенде выполняет демонстрационный скрипт после проверки, что старый master остановлен;
  для автоматического production-failover нужен оркестратор вроде Patroni;
- HA-профиль использует отдельные очищаемые тома на одном хосте и предназначен для
  локального demo; production требует независимых узлов и автоматического failover/discovery.

## 3. Демонстрация failover

`scripts/demo_ha.sh` выполняет оба обязательных сценария:

1. **5.1 PostgreSQL:** проверяет master/standby, пишет данные в master, ждёт
   репликацию, аварийно завершает master через выбранный контейнерный движок, выполняет
   `pg_ctl promote` и проверяет чтение/запись на новом master.
2. **5.2 RabbitMQ:** собирает трёхузловой кластер, создаёт quorum queue,
   публикует persistent-сообщение, аварийно завершает leader и проверяет на
   standby как старое сообщение, так и публикацию нового.

Запуск:

```sh
sh scripts/demo_ha.sh
```

## 4. Резервное копирование БД

- **`scripts/backup.sh`** — дамп `pg_dump` в `backups/rail_repair_<дата>.sql.gz`, ротация: хранятся последние 7 копий.
- **`scripts/restore.sh <файл>`** — восстановление из дампа.
- Расписание — cron на хосте: `0 3 * * * /path/to/scripts/backup.sh` (RPO ≤ 24 ч).

### Сценарий проверки на защите
1. Создать заявку → `scripts/backup.sh`.
2. Удалить заявку (или всю таблицу).
3. `scripts/restore.sh` → заявка на месте.
